name: complete-audit
description: Find due audits, read their stages and requirements, draft safe returned documents, upload and attach evidence, then hand review and sign-off to the person.
---
## Task
Help prepare the current audit's evidence and returned document. A prepared return is separate from reviewer acceptance or closure.

## Method
For every step use the named MCP tool if listed and permitted. If absent, use that step's Chrome path. If refused, explain the refusal, offer Chrome and wait for yes. A failed step stops and follows `guides/recording.md`. Confirm each write and its result note. Never use another key, account or workspace to work around refusal.

1. Find due and overdue work using `list_audit_cycles` if listed, with the live schema and requested time window. Today follow `my-tasks` to `/tasks`, **My tasks**, **Overdue** or **Due today**, then inspect all open work for upcoming audit stages. `list_tasks` can help only with a verified user ID, `status: "open"`, `assignee: "user:<verified-uuid>"`, `include: "stages"`, `limit: 50`. Say the list may be incomplete at 50 and use Chrome. If an expected audit has no cycle, report that fact and ask its owner about setup; never create, approve or reschedule a definition to make work appear.
2. Read `get_audit_cycle` if listed. Today click the audit task's title in `/tasks` and open its stage tracker. Read its captured stages, due date, required evidence rows, instructions and **Reference** documents. **Previous cycle**, **Open** shows the previous cycle where present. Each **Reference** document has a title link and **Download**. `get_task` provides only a parent summary and document names; it is not the audit pack. If an instruction or return template is missing, stop and tell the person exactly which source is missing. Never invent an audit question or procedure.
3. Ask the person to confirm all sources are free of identifiable clinical data before opening them. Use `search_documents` for supporting Library evidence after confirming the search-job write, or `/documents`, **Library**, **Filter by file name**, **Type**, then a document title. Follow `find-document` for citations and safe downloads into `downloads/`. Use the current cycle's instruction package and its returned document. Prior-cycle documents are examples and references, never proof that work was performed this cycle.
4. Ask the person for the counts, summaries, dates and observations they prepared outside the clinical records system. Do not inspect that system, request records, invent performed work, fill missing results from last cycle, or sign for anyone. Draft answers in the returned document, preserving its questions and structure. Show the proposed edits and obtain confirmation before saving. Use desktop control only for a native editor the person names, such as Word, and only on a safe screen. If editing support for that file is unavailable, provide the approved answer text for the person to enter; do not claim the document was saved. Never use desktop control while clinical records are on screen.
5. For new evidence use listed `upload_document` only with a safe local-file transfer capability. No direct upload script ships in this kit today, so use Chrome if that capability is absent, explaining the limit and waiting for yes after a refusal. Open the audit again, locate the exact named evidence requirement and its type, then **Upload a <live type name>**. At **Choose a file**, use Claude in Chrome's file-upload capability for the confirmed current safe return, check its locked **Document type**, enter **Description**, then **Upload document** after confirmation. Only if Chrome file upload is unavailable, explain the limit and ask whether the person will choose the file or wants their named native file picker controlled. For an existing Library file use the row's **Attach a <live type name>**, enter its name into **Search the Document Library**, verify the matching safe file and obtain confirmation before clicking that file's row. Clicking the row immediately attaches it; there is no separate save button. Do not guess a document from its name alone.
6. If `attach_audit_evidence` is listed, use the cycle ID, current requirement key and document ID according to its schema, after confirmation. Today the row-specific Chrome upload or attach preserves the requirement identity. Never replace that with `attach_document_to_task`, which only creates an ordinary document link and cannot identify the named audit requirement. Check the requirement result after upload. A file in the Library is not proof of successful attachment. If it remains outstanding, report why and stop. Do not upload again to repair an unknown attachment outcome.
7. Verify the current return is linked to its exact requirement, indexing has finished where required, and no required evidence or answers are missing. Record each save, upload, attachment and failure on the audit task using `comment_on_task`, or **Notes**, **Add a note**, **Add note**, following `guides/recording.md`. Include the requirement and document references and any remaining blocker. Say “ready for the reviewer” only when the visible requirements and returned document support that statement. Do not mark a review or audit stage done to submit it.
8. Open the relevant **Audit review** screen and hand control back. Hand-back only: **Mark sample or inputs ready**, **Confirm actual event**, **Confirm completed**, **Record not applicable**, **Confirm completed check**, **Confirm external source**, **Formally defer**, the **What did you verify?** dialog and its **Confirm** button, **Accept <document>**, **Send back to the owner**, and **Accept and complete the review**. Never fill or submit these controls, reviewer checkboxes, deferral reasons, governance attestations or audit closure confirmations. A requirement confirmed without an attached file is always the person's to confirm. A person's general "yes" never authorises these controls. Explain what the person must inspect. Only describe a human decision as recorded after the person finishes and its resulting state can be safely read. Do not claim closure from an upload or a comment.

## Requirements
An existing audit cycle, accessible instruction package and return document, safe evidence, the person's factual inputs and an associated audit task. Missing setup, source bindings or safe editing support blocks the affected step. Claude in Chrome is the full audit-pack and evidence path today. Native control is only for the person's named safe editor or file picker.

## Reference files
`CLAUDE.md`; `guides/filing.md`; `guides/recording.md`; the `my-tasks`, `find-document` and `file-document` skills.

## Result
Give the cycle link, returned document, evidence per requirement, verified task notes and any blockers. State whether preparation is ready for human review. Reviewer decisions, deferrals, attestations and closure remain with the person.

## Tools and integrations
Nurture MCP when listed: `list_audit_cycles`, `get_audit_cycle`, `list_tasks`, `get_task`, `search_documents`, `get_document`, `upload_document`, `update_document_metadata`, `attach_audit_evidence`, `comment_on_task`. Chrome: `https://app.nurtureoutreach.com/tasks`, `/documents` and selected document pages. Native editor: only as requested by the person.
